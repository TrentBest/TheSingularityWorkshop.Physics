# Geometry Foundation: 2D Vectors

**Status:** finite 2D vector arithmetic, exact-sign orientation, closed-segment intersection classification, unique-point intersection construction, explicit absolute-distance tolerance, frame-tagged point identity, and frame-aware rigid 2D transforms are implemented. A complete geometry/collision API is not implemented.

## Contract

[`Vector2d`](../Physics/Spatial/Vector2d.cs) represents two finite, unit-agnostic components. It provides addition, subtraction, scalar scaling/division, squared length, length, dot product, signed 2D cross product, and squared distance. Focused tests live in [Vector2dTests](../tests/TheSingularityWorkshop.Physics.Tests/Math/Vector2dTests.cs).

[`CoordinateFrame2d`](../Physics/Spatial/CoordinateFrame2d.cs) provides a stable, non-empty, ordinal/case-sensitive identifier for a caller-defined frame. The owner must document its origin, axes, orientation, and coordinate units; the identifier does not define a transform or prove compatible conventions. [`Point2d`](../Physics/Spatial/Point2d.cs) pairs coordinates with that identity, includes the frame in exact equality, and exposes `RequireSameFrame` to reject comparisons across different frame IDs. [`RigidTransform2d`](../Physics/Spatial/RigidTransform2d.cs) maps points between explicit source and destination frames using counter-clockwise radians and destination-frame translation. It supports direction-only rotation, inverse, and ordered composition (`first.Then(next)` means apply first, then next); point application and composition reject frame mismatches. Focused tests are in [CoordinateFrame2dTests](../tests/TheSingularityWorkshop.Physics.Tests/Math/CoordinateFrame2dTests.cs) and [RigidTransform2dTests](../tests/TheSingularityWorkshop.Physics.Tests/Math/RigidTransform2dTests.cs).

For three points, [`Geometry2d.Orient`](../Physics/Spatial/Geometry2d.cs) returns `CounterClockwise`, `Clockwise`, or `Collinear`. A conservative floating-point filter uses exact integer arithmetic over represented binary64 coordinates when the filter cannot safely determine the sign. This is exact classification of supplied values, not a claim that measured inputs are physically exact. See [Geometry2dTests](../tests/TheSingularityWorkshop.Physics.Tests/Math/Geometry2dTests.cs).

[`Geometry2dSegments.ClassifyIntersection`](../Physics/Spatial/Geometry2dSegments.cs) classifies two closed segments as disjoint, proper intersection, endpoint touch, collinear overlap, or degenerate-point intersection. [`Geometry2dSegments.Intersect`](../Physics/Spatial/SegmentIntersection2d.cs) returns that classification plus a coordinate only when there is a unique point; disjoint segments and collinear overlaps have no unique point. Endpoint and degenerate intersections reuse an input coordinate. Axis-aligned proper crossings also reuse their exact input x/y coordinates. General proper crossings now form exact integer line equations from the supplied binary64 coordinates using a shared power-of-two representation, calculate the rational intersection with `BigInteger`, then convert the result back to binary64 without first converting huge integers directly to `double`. This avoids losing a tiny segment solely because another endpoint has a much larger magnitude. The final rational-to-binary64 conversion is rounded, not an exact-real output guarantee; measured input uncertainty remains outside the predicate. Regression tests cover extreme mixed-scale axis-aligned and non-axis-aligned crossings, a subnormal-scale intersection coordinate, and a non-dyadic rational crossing whose result must be rounded back to binary64. See [SegmentIntersection2dTests](../tests/TheSingularityWorkshop.Physics.Tests/Math/SegmentIntersection2dTests.cs). See [Geometry2dSegmentsTests](../tests/TheSingularityWorkshop.Physics.Tests/Math/Geometry2dSegmentsTests.cs) and [SegmentIntersection2dTests](../tests/TheSingularityWorkshop.Physics.Tests/Math/SegmentIntersection2dTests.cs).

[`GeometryTolerance2d`](../Physics/Spatial/GeometryTolerance2d.cs) makes a caller-selected absolute Euclidean-distance threshold explicit. Its value must be finite and non-negative and uses the same coordinate units as the points. `IsNear` performs a scaled distance comparison to avoid squared-distance overflow. There is no universal default: the appropriate tolerance depends on coordinate scale, units, source uncertainty, and the decision being made. See [GeometryTolerance2dTests](../tests/TheSingularityWorkshop.Physics.Tests/Math/GeometryTolerance2dTests.cs).

[`Geometry2dPolygon.SignedArea`](../Physics/Spatial/Geometry2dPolygon.cs) computes the signed shoelace area in O(n), positive for counter-clockwise order and negative for clockwise order. It accumulates the products exactly over the supplied binary64 coordinates with `BigInteger`, then rounds the final result to binary64 using nearest/ties-to-even; this avoids intermediate product overflow and cancellation in the accumulation. It throws if the exact area magnitude rounds beyond the finite binary64 range; a nonzero exact area below the representable range can underflow to zero. For self-intersecting boundaries, the result is algebraic shoelace area, not the sum of the filled regions; use `IsSimple` when simple-polygon semantics are required. Exact accumulation allocates and is not a GPU kernel. Focused tests cover winding direction, a repeated closing vertex, concavity, algebraic cancellation, large finite and tiny coordinates, and overflow. [`Geometry2dPolygon.Triangulate`](../Physics/Spatial/Geometry2dPolygon.cs) performs O(n²) ear clipping and returns `TriangleIndices2d` triples into the original effective boundary, preserving clockwise or counter-clockwise winding and returning n−2 triangles. It requires a simple boundary and rejects consecutive collinear triples rather than silently dropping vertices; a repeated closing vertex is excluded from the index domain. Convex ears are selected with the exact-sign orientation predicate, and candidate ears containing another remaining vertex on or inside the triangle are rejected. Tests verify triangle count, winding, summed signed area, concave boundaries, repeated closure, invalid input, subnormal-scale polygons whose rounded area is zero, and extreme finite coordinates whose area magnitude cannot fit in a `double`. A concave comb-shaped polygon is now tested in both winding directions; its triangles must have matching winding, centroids inside/on the boundary, and summed signed area equal to the polygon area. This is a bounded simple-polygon triangulator, not a constrained-Delaunay or quality-mesh implementation. [`Geometry2dPolygon.IsSimple`](../Physics/Spatial/Geometry2dPolygon.cs) checks whether a boundary is simple in O(n²), allowing an optional repeated closing vertex but rejecting fewer than three distinct vertices, repeated vertices, zero-length edges, non-adjacent crossings/touches/overlaps, and adjacent-edge overlap/backtracking. Adjacent edges may meet at their shared endpoint. It uses exact represented-coordinate segment predicates and no proximity tolerance. [`Geometry2dPolygon.LocatePoint`](../Physics/Spatial/Geometry2dPolygon.cs) classifies a point against a simple polygon using the non-zero winding rule and the exact-sign orientation predicate. It distinguishes `Inside`, `Outside`, and `Boundary`; edges and vertices count as boundary. Supply at least three vertices in boundary order; the first vertex need not be repeated. Clockwise and counter-clockwise vertex order are both supported. Regression tests also cover very large finite coordinates (including a point outside a polygon whose edges are near the binary64 maximum), subnormal-scale polygons, a repeated closing vertex, and a horizontal ray aligned with polygon vertices, checking inside/boundary/outside outcomes. Point location does not repair self-intersections or apply a proximity tolerance; constrained-Delaunay triangulation, mesh-quality criteria, and broader region operations remain unimplemented. See [Geometry2dPolygonTests](../tests/TheSingularityWorkshop.Physics.Tests/Math/Geometry2dPolygonTests.cs).

## Deterministic procedural samples

[`SeededPointSet2d`](../Physics/Spatial/SeededPointSet2d.cs) generates up to 65,536 2D points in a finite half-open rectangle from a 32-bit seed. Each coordinate is derived from the point index and an axis-specific Squirrel3 hash domain, so results are independent of mutable stream call order. The returned list is read-only, ordered by generated index, and can contain duplicate points. Focused tests live in [SeededPointSet2dTests](../tests/TheSingularityWorkshop.Physics.Tests/Spatial/SeededPointSet2dTests.cs); the current class diagram is [SeededPointSet2d UML](UML/SeededPointSet2d.svg).

This is a reproducible sampling primitive, **not** a probability distribution beyond its declared hash-to-range mapping, a Poisson-disc sampler, a collision-free packing, a fractal generator, or a physical material model. It is a small data-generation proof that can be consumed by downstream visualization without making SVG or renderer packages dependencies of Physics.

## Deliberate limits

- Frame identifiers are labels, not a unit system or transform graph. Reusing an identifier for inconsistent conventions is a caller error. `RigidTransform2d` provides explicit pairwise conversion, not a graph, automatic path finding, unit conversion, or convention discovery.
- Raw `Vector2d` operations remain frame-agnostic; use `Point2d` where frame identity matters.
- Equality is exact component equality. A tolerance comparison is a separate explicit operation, not a replacement for equality or robust orientation.
- Tolerance-based proximity does not alter segment intersection classification. A near miss remains disjoint under the exact represented-coordinate classifier, even if a domain-specific solver later chooses to treat it as contact.
- The type rejects non-finite inputs and arithmetic results that overflow to non-finite values. Some finite squared lengths can still overflow; scaled norm helpers remain future work.
- Exact orientation fallback prioritizes correctness over throughput and is not a GPU kernel. The tolerance policy is scalar CPU code and does not represent measurement uncertainty unless the caller chooses a threshold from an explicit uncertainty model.

## Next geometry slices

1. Continue adversarial intersection-coordinate analysis: tests now check subnormal-coordinate accuracy and non-dyadic rational rounding, but correctly-rounded conversion, ill-conditioned error bounds, and a caller-visible accuracy policy remain open.
2. Add transform graph/path policy only when a consumer needs more than explicit pairwise transforms; define cycle and consistency behavior.
3. Expand polygon triangulation with adversarial and numerical-range tests; the current ear-clipping implementation deliberately rejects consecutive collinear triples and does not optimize mesh quality. Filled-region area for self-intersecting boundaries remains a separate policy.
4. Add batch/SoA equivalents only where they share scalar reference fixtures and declare whether they preserve exact or approximate predicate semantics.

These primitives establish a reusable geometry vocabulary; they are not evidence that a general geometry engine exists.
